# Contract schemas

<!-- The JSON Schemas of the data Debuggatha stores and exchanges; for adapter authors. -->

JSON Schema (draft-07) for the data Debuggatha stores and exchanges. They are the target the Rust engine must reproduce (ADR-0006) and the shapes [PROTOCOL.md](../PROTOCOL.md) refers to.

| `review-request.schema.json`, `review-session.schema.json` | One requested review, and the record of one in progress (lifecycle status, selected policy and packs) | Engine-internal; **generated from Rust** |
| `review-scope.schema.json` | What a review covers (workspace, diff, files, changes) | Engine input |
| `review-changes.schema.json` | Introduced, fixed and reopened findings of a run | Engine output |
| `analyzer-options.schema.json`, `analyzer-run.schema.json` | Which analyzers may run, and what happened | Engine input and output |

| `review-job.schema.json`, `review-job-result.schema.json` | The former VS Code worker job, the closest existing form of a protocol request; `apps/vscode/src/contracts` is generated from `ledger`, `repository-context` and `review-job-result` | `apps/vscode/src/daemon/api.ts` |

## How they were made

Generated from the TypeScript types of version 0.2.0 with `ts-json-schema-generator` (`--no-type-check`, additional properties off), then hardened by hand in one place: `Finding.evidence` and `Finding.locations` have `minItems: 1`, because "a finding must point at something and be backed by evidence" is a runtime check in `createFinding` that the types do not express.

Reviewed by hand in phase 0 (see "Review pass" below). They are a snapshot, not yet generated by the build. Generation from the Rust types with `schemars` has started: the files marked "generated from Rust" (`finding`, `ledger`, `repository-context`, `review-request`, `review-session`) are written by `generated_schema` and a test fails when they are stale. `generated_schema` closes objects, drops `null` from optional fields (absent is how a file says "none") and strips `uint32` noise; `finding` and `ledger` were checked to be equivalent to the hand-reviewed versions they replaced (same properties, required fields, enums and minimums; only definition names differ, e.g. `PackReference` for `ReviewPackReference`) and every one of the 7,736 corpus findings validates. Still hand-reviewed, and why: `memory-store` (the Rust item is one struct with a `category`, the schema is a stricter union of six kinds; the Rust-written store is validated against it), `review-result` (needs `Coverage`, an engine type), and `baseline`, `review-changes`, `analyzer-*`, `semantic-run`, `review-job*`, `review-scope` (engine types, not ported yet). They move over as their types are ported.

## Validation done (phase 0.2)

Checked with Ajv against real output of the TypeScript engine:

- 6 CLI reports (dart-sei, obfusku, pm2-eid-is-discord, promediatum, express, zod): all `reviewResult` objects valid, 4,358 findings in total.
- A `ledger.json` and a `baseline.json` produced by the CLI.
- A `memory.json` produced by `core` containing all six item kinds and the detected, suggested, confirmed and active transitions.
- Negative controls that must be rejected, and are: finding without evidence, empty evidence, empty locations, no locations, severity `urgent`, unknown field, ledger entry with status `bogus`.

Not yet covered: `review-job` and `review-job-result` against real VS Code worker traffic, and the CLI report envelope (no named type; see PROTOCOL.md, section 10).

## Review pass (phase 0, after the first generation)

Fixed by hand, because porting the TypeScript types as they were would have frozen their defects into the contract:

- Counters, durations, lines and columns are `integer` with a minimum (0 for counts and durations, 1 for lines, columns, `timeoutSeconds` and `schemaVersion`), not `number`. Timestamps (`*At`) carry `format: date-time`.
- Removed the leaked TypeScript function `analyzers.enableHint` from `review-job` and `analyzer-options`; corrected the `scope` description (the generator had attached the comment of `executeReview`).
- `review-job-result` references `AnalyzerRun`, `SemanticRun` and `Finding` instead of repeating them, and gained the protocol fields: `findingsPage` (`findings`, `truncated`) and the alternative answer `ReviewInputRequired` (`status: "input_required"`, `token`, `expiresAt`, `inputs`).
- New `Coverage` (in `review-result` and `review-job-result`; optional so reports of the TypeScript reference engine stay valid, always emitted by the native engine):
  - `complete`: derived by the engine, true only when every language is fully parsed, no rule has a gap (except `disabled-by-config`, the person's own choice) and no file was skipped for a reason that hides code (`too-large`, `unreadable`, `not-utf8`; `ignored`, `binary`, `generated`, `symlink-outside-root` are scope decisions).
  - `languages`: per language, files, files with errors, status (`parsed`, `parsed-with-errors`, `parsed-limited` for partial grammars such as C++, `not-parsed`) and parser. `fileDetails` (one entry per file) appears only when the job sets `coverageDetail: "files"`; the default is `summary`, so the report does not grow with the repository.
  - `checkedRules`: rules evaluated, per pack and version. With `ruleGaps` it accounts for every rule of the active packs.
  - `ruleGaps`: `no-detector`, `needs-type-information`, `needs-repository-files`, `language-not-parsed`, `analyzer-not-installed`, `analyzer-not-enabled`, `analyzer-failed`, `timeout`, `disabled-by-config`.
  - `skippedFiles`: by reason (`ignored`, `binary`, `generated`, `symlink-outside-root`, `too-large`, `unreadable`, `not-utf8`).

Still open: `Category` accepts any string, since packs are data and may add categories; whether to close it is decided when packs become JSON (phase 4).

Checked again with Ajv after the changes: the same real data passes and the same negative controls are rejected, plus 17 new cases for the changed schemas (counts that are negative or fractional, bad coverage status, `input_required` with and without inputs, the removed `enableHint`).

## Strict stored files, tolerant wire

The schemas reject unknown fields, which is right for files on disk (they carry `schemaVersion` and a migration path). Protocol messages use the same shapes but receivers ignore unknown fields (PROTOCOL.md, section 2), so adding an optional field does not break an older client.
